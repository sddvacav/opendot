# 立党近期公开发言与 OpenDot 产品假设

研究截止 2026 年 10 月 1 日。检索范围以最近 30 至 60 天为主；核心证据是直接打开核验的 5 条 2026 年 9 月 X 原帖，另以两个公开 GitHub 项目补充实际工作方式。本文研究公开观点，不代表对方有采购意愿、正在使用 OpenDot，或认可 OpenDot。

## 结论

最值得测试的定位是：**面向可验收的长任务，把多个 agent 的持续执行、独立验证、失败恢复和结果交付组织起来。**

立党的近期观点支持这类探索，尤其是数学、计算、仿真等能在计算环境内获得反馈的任务。但他对通用业务编程中继续堆 agent 的增益明显持怀疑态度。因此，仅展示大量终端、多个角色同时发言，或承诺自动替代程序员，未必能打动他；更有说服力的是一项可复现任务的完整验收记录，以及减少了多少人工照看的证据。

这是基于公开发言的产品推断，并非他的原话，也不是经客户访谈确认的需求。

## 五条核心原帖

### 1 结果是否可信 是多 agent 的核心问题

- 原站显示：2026 年 9 月 4 日 20:29
- [X 原帖](https://x.com/lidangzzz/status/2096078265534292180)
- 已核验的公开观点：他主张先明确定义任务边界、测试和验收条件；不同 agent 的产出要经过独立质疑、review 和测试，不能直接信任。还明确描述了用户面对大量产出，却不知道是否正确、完整的焦虑，并接受以额外 token 换取更可靠的交付或明确失败。
- 对 OpenDot 的推断：主界面应优先说明“验收通过了什么、还缺什么、谁验证过”，而不是只显示 agent 正在忙。值得测试的能力包括独立验证者、可执行验收器、失败状态及证据链接。
- 证据边界：文中的 token 与可靠性提升数字属于他的表达，没有配套实验，不能转成产品性能承诺。

### 2 长时并行要选对场景

- 原站显示：2026 年 9 月 5 日 15:28
- [X 原帖](https://x.com/lidangzzz/status/2096364825072804152)
- 已核验的公开观点：他认为多数业务编程仍需要频繁的人与 agent 交替；对数学任务则看好长期循环和多个 agent 同时工作，并举到 20 个 agent、100 小时量级的工作方式。
- 对 OpenDot 的推断：先用研究计算或有明确测试判据的任务证明价值。长时运行的卖点应落在掉线恢复、保留状态、避免空转、可终止和完成验收上。
- 证据边界：这些是其观点及自述，不是经独立核验的持续运行基准，更不证明增加并行度就会线性增益。

### 3 人需要介入多少 取决于任务反馈是否封闭

- 原站显示：2026 年 9 月 7 日 14:56
- [X 原帖](https://x.com/lidangzzz/status/2097081516371361994)
- 已核验的公开观点：他区分了紧贴业务、涉及组织协作的编程工作，与编译器、基础设施、数学、仿真计算等更容易在本地测试的工作；认为后者更适合长时自主执行。
- 对 OpenDot 的推断：产品需要让用户显式选择人工决策点与自动验收点，适配真实项目的边界。可演示“遇到业务歧义就停下提问，确定性计算与测试自动推进”。
- 证据边界：他关于各类工作占比及替代率的数字未经验证；复杂系统是否可以被本地测试充分覆盖，也不能一概而论。

### 4 科学工作需要完整成果链

- 原站显示：2026 年 9 月 12 日 0:19
- [X 原帖](https://x.com/lidangzzz/status/2098672784754819562)
- 已核验的公开活动：他发布 The Last Math Competition，计划批量生成猜想，由人和 agent 评估，再以 PR 提交包含 LaTeX、PDF、Lean 4 项目的证明或反例，review 后合并，并持续登记结果及反馈改进。原帖同时承认早期猜想质量可能差。
- 对 OpenDot 的推断：一个有针对性的演示应从任务进入队列，一直走到可下载、可复核的成果包；同时记录拒收原因、未完成项和下一步。完成率与有效成果数比聊天量更有价值。
- 证据边界：发布规则不等于已实现每周规模或已证明科研突破。不要把他提出竞赛写成 OpenDot 已获得科研客户验证。

### 5 信任边界会影响部署选择

- 原站显示：2026 年 9 月 21 日 11:29
- [X 原帖](https://x.com/lidangzzz/status/2102102874876436926)
- 已核验的公开观点：他分别讨论模型厂商、推理服务商与 agent/workflow 框架的信任，预测部分组织会拆分供应链、采用开源及自控部署，甚至把计算放在自有设施内。
- 对 OpenDot 的推断：若产品面向有私有代码、研究数据的团队，介绍时应把数据去向、模型选择、执行位置、权限边界讲清楚。若实际支持本地或自托管，应以可验证的架构说明展示；未实现的能力不能先当卖点。
- 证据边界：这是他对市场的预测，不能推断他本人需要本地 GPU，也不是所有中国客户的统一需求。

## 两个公开项目带来的补充判断

以下仓库为2026-10-01读取的动态README快照；未固定不可变提交，不用于精确代码或后续状态结论。

### Goal Driven 是已存在的替代方案

[公开仓库](https://github.com/lidangzzz/goal-driven)将明确目标和验收标准置于核心，由主 agent 检查子 agent 的结果与活动状态，未达标则继续。仓库提供提示词模板，并列出编译器、数据库等例子。当前 README 的持续时长表述超过 300 小时，而仓库简介仍写约 100 小时；均为项目方声明，本次没有运行复现。

**推断：** OpenDot 的比较对象包括“用户给现有 coding agent 一段提示词”。若希望此类重度用户切换，需要证明状态持久化、恢复、隔离、验收或管理负担有实质改善。仅将提示词包成界面，不足以从这些资料中推出明确优势。

### 数学竞赛的要求能成为窄场景验收清单

[竞赛公开仓库](https://github.com/The-Last-Math-Competition/The-Last-Math-Competition)与发布帖的工作流程基本一致。它是可用的公开任务规格线索，能够启发成果格式、元数据和评审环节设计。

**推断：** 可先在自有演示仓库复现同类流程，验证端到端交付，不必立即向原项目提交内容。自动向他人的项目发 PR、写评论或联系本人，是另一项需要明确授权的外部行动，本次没有执行。

## 七个值得验证的产品假设

以下全部为研究推断，不应写成“立党提出的 OpenDot 需求”。

1. **验收可见性**：用户愿意为清楚知道哪些结果可信、哪些尚未验证付出成本
2. **长时可靠性**：持续工作数十小时的恢复能力，比同时打开更多聊天窗口更重要
3. **场景选择**：边界明确、反馈可执行的研究任务，更适合作为首个可复现实验
4. **人工介入设计**：真正需要人的判断应集中暴露，避免每几分钟都要用户检查运行状态
5. **成果交付**：代码、报告、测试记录与失败说明应成为同一任务的可审查成果包
6. **成本与停止机制**：重度使用不等于无限预算，应提供预算上限、空转识别及可恢复停止
7. **可信部署**：数据与执行位置透明、权限可审计，可能影响专业用户的采用

其中“预算上限、空转识别、可恢复停止”是从长任务风险推导出的设计建议，五条 X 原帖没有直接提出这些功能。

## 对产品展示的建议

建议准备一个小而完整的可复现实验，不先宣传解决开放科研难题：

- 选有公开输入、明确输出与机器验收条件的任务，例如给定规格的实现与差分测试，或已知数学命题的形式化复现
- 运行前固定验收标准，保留任务版本、模型与执行环境信息
- 展示一次中断与恢复，以及一个真正失败并被明确识别的子任务
- 输出完整成果包，并让独立环境重跑验收
- 同时报告总耗时、费用或 token、人工介入次数、验收通过项、失败项和可复现程度
- 与现有 coding agent 配合简单 goal-driven 提示词的方式比较，而不只与人工从零工作比较

这组比较能检验 OpenDot 的新增价值。未运行实验前，不承诺无人值守时长、并发收益、成功率或成本节省。

- 形式化工具接受某个形式命题，不自动证明它忠实表达了原始科学问题；验收仍要审核任务定义
