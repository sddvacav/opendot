# Siemens EDA 行业案例与 OpenDot 验收建议

核查日期：2026 年 10 月 1 日。用途是把公开行业案例转化为 OpenDot 可验证的产品假设与验收任务。资料来自 Siemens 官方新闻稿和产品博客；它们能证明厂商的公开发布与主张，不能代替独立性能评测、客户采购需求或 OpenDot 的实测结果。

## 核心判断

这个案例最有价值的启示是：工业 agent 的价值要通过已有专业工具验证，并贯穿整个长任务，而不能仅靠模型宣布完成。跨工具编排、恢复与治理同样重要，但都应服务于最终合格成果。

对 OpenDot，建议先建立“执行有回执、结果有判据、失败可追踪、恢复不失控”的通用基础，再选择一个窄领域做连接器与验收示范。没有必要先追求完整 EDA 产品线覆盖，更不能从通用编排能力推导出已具备芯片签核能力。

下面的功能映射全部是候选设计和验收建议。本次没有审计 OpenDot 当前实现，没有运行 EDA 工具，也没有核实它与 Siemens 或 NVIDIA 的兼容性。

## 需求 功能 验收 优先级映射

优先级是本报告对 OpenDot 的建议，不是 Siemens 的产品路线图，也不是承诺上线时间。

- **P0**：任何专业长任务试点之前应有的安全与可信完成基础
- **P1**：选定一个领域试点时完成的集成与测量
- **P2**：已有可靠基线后再增加的优化

| 公开案例启发的需求 | OpenDot 候选功能 | 建议验收方式 | 优先级 |
|---|---|---|---|
| 专业结果需要外部判据，不能只信 agent 自评（S2） | 将工具执行、产物生成、领域验证、人工批准分成不同状态；验证器给出通过、失败或未知 | 预设合法、错误、缺失证据、超时四类输入；未知不能被汇总为通过；在冻结的已知错误集上记录错误接受率，不能用一次全拒收宣称普遍零误报 | P0 |
| 长任务必须能从失败中恢复（S1） | 持久任务状态、检查点、重试策略、外部作业对账、取消与恢复回执 | 在提交前、提交后未记账、结果返回前后分别注入中断；恢复后与外部作业身份对账，避免重复提交产生未授权额外成本；不可确认时暂停并报告 | P0 |
| 设计 IP 需要明确边界（S1） | 每任务权限范围、工具白名单、网络出口策略、敏感值遮蔽、审计记录 | 越界文件访问与未授权出口应被阻断；日志不包含测试密钥；断开外网时验证选定离线流程。未做隔离测试，不宣称气隙或企业安全认证 | P0 |
| 工业决策需要责任和批准（S1） | 将高成本重跑、覆盖有效产物、发布交付物等步骤设为可配置审批点，并限定已批准范围 | 未批准时不能越过检查点；批准只覆盖指定目标和版本；审批失效、目标变更或预算增加时重新阻断 | P0 |
| 多工具、多格式会造成语义丢失（S1） | 版本化工具契约与领域连接器，明确输入输出、单位、环境依赖和失败语义 | 同一最小流程在连接器测试中检查产物可读性、参数传递与版本兼容；用错误单位、过期格式、缺依赖案例测试拒绝行为；不得只以退出码 0 认定有效 | P1 |
| 大规模运行依赖现有算力和调度设施（S1） | 外部作业身份、资源配额、许可证约束、排队与运行状态分离 | 模拟队列等待、许可证不足、抢占、节点失联、超时与用户取消；预算达到限制时不新增作业；清楚记录已经发生及可能仍发生的成本 | P1 |
| 工程师需要可检查的最终成果（S2） | 成果包与来源清单，绑定输入、工具版本、配置、检查结果和局限；保留失败尝试 | 在另一受控环境重放一个许可明确的样例；验证所有交付物可定位、可打开，与验收回执一致；缺失或篡改依赖应导致重新验证而非复用旧通过状态 | P1 |
| 提速与降成本必须有公平基线（S3） | 固定评测协议和全量成本账，比较达到相同质量门槛的结果 | 冻结任务集、工具权限、硬件、模型、预算和基线；统计所有尝试，报告合格率、人工时间、墙钟时间及成本；分别列排队、工具计算与模型耗时，不移植厂商倍数 | P1 |
| 改进流程不能污染可信状态（S2） | 把历史经验与已验证产物分开保存；流程变更需重新资格测试 | 修改模型、提示、连接器或求解器后，定位受影响结果并失效旧判定；只有通过冻结回归集的候选才进入默认流程，失败优化可回退 | P2 |

## 建议的最小演示边界

建议先完成一个离线、许可明确的合成工作流验收包。它可以验证编排基础，但不能称为 EDA 性能验证。

1. **正常交付**：几个有依赖关系的工具步骤生成一份结果，再由独立检查程序判定；最终输出可重放成果包
2. **结果无效**：工作进程正常退出，但产物故意包含错误；系统应识别失败而非宣布任务完成
3. **长任务中断**：在外部作业已经启动、控制器尚未记录成功时中断；恢复后应对账而非盲目重复提交
4. **范围越界**：子任务请求额外数据、出口或超预算执行；系统应阻断并说明所缺授权

每个案例的预期结果应在运行前冻结，并由不负责生成结果的检查路径验证。验收表应记录实际结果，不允许只展示成功视频。

进入真实行业试点的下一步，是与合法工具和数据持有方共同确定一个窄流程、工具许可、数据分类、算力配额与验收权责。这些条件未确认前，不能声称已完成 Siemens 集成、真实工艺验证或工业级签核。

## 性能与宣传口径

### 可以公开采用

“Siemens 在 2026 年公开描述的 EDA agent 架构，强调跨工具编排、持续专业验证和运行治理。OpenDot 将这些公开行业案例作为需求假设来源，并以独立、可重放的验收来检验自身实现。”

采用这句话时，应同时披露 OpenDot 实际完成的验证范围，不能让读者以为所有候选能力均已实现。

### 不能采用

- “Siemens 或 NVIDIA 推荐、采用或认可 OpenDot”
- “OpenDot 已达到 Fuse 的性能或安全水平”
- “Siemens 证明所有多 agent 系统都能提速十倍”
- “生成有效文件就等于设计可流片”
- “有确定性验证器就保证原始需求、模型和边界条件都正确”
- “厂商博客展示无人值守，因此企业可以取消人工批准或责任归属”

### 数字使用限制

厂商数据只用于理解其宣传的价值方向。若引用倍数，必须紧邻注明 Siemens 的自述、具体来源和案例范围，不用于 OpenDot 自身的 KPI、对比图或投资回报估计。不能把不同阶段的耗时改善、token 成本与额外优化比例相乘，拼成更大的总收益。

## 尚缺证据

- 真实 EDA 用户对当前瓶颈、失败成本、审查责任和支付意愿的访谈
- 对上述厂商倍数的独立复现，以及完整评测协议
- 扩展能力逐项的正式版本、许可与可用性确认
- OpenDot 现有实现到候选功能的覆盖审计与实测
- 真实专业工具、工艺库与设计数据的合法接入和重放

本次仅进行了公开资料核查和文档编写，没有访问冻结仓库、调用模型供应商执行接口、运行 EDA 软件、提交外部内容或发布文档。
